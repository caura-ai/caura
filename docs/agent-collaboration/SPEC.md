# Caura agent collaboration (0.2 preview)

This specification supersedes the original shared-Redis V1 design. All exchanges
must traverse Caura: sending, claiming, acknowledging, renewing, retrying,
replying, discovery and conversation history.

## Identity and authorization

The official Enterprise auth service validates agent credentials. The gateway
overwrites all identity/capability headers and supplies its internal secret.
Caura core API's existing authentication dependency resolves identity; the bus
extension additionally requires the verified gateway, agent-key kind, tenant,
agent and explicit read capability. Mutations require write capability and
pass existing usage gates.

There is no client-supplied sender or tenant field on send, no direct Redis mode
and no fallback when Caura is unavailable. Configured identity is an expectation,
not authority. Agent records are the existing Caura tenant-scoped records.
Same-tenant agents may message one another. Local peer lists are a convenience,
not a substitute for future server-managed peer policy.

## Public API

All endpoints are under `/api/v1/bus`.

| Operation | Endpoint |
|---|---|
| Verify identity | GET /identity |
| Registered peers | GET /agents |
| Live capability discovery | GET /discover |
| Advertise session | PUT /presence |
| Resumable live events | GET /events?after=SEQUENCE |
| Evaluate a runtime checkpoint | POST /checkpoints |
| Explicit request for a human | POST /interventions |
| Accept a message | POST /messages, required Idempotency-Key |
| Lease one delivery (SDK) | POST /inbox/claim |
| Session-owned long poll | POST /inbox/wait (session_id, timeout=20; maximum 20) |
| Non-consuming wake hint | GET /inbox/state (pending, active, awaiting_reply, wait_generation, cursor) |
| Atomic reply / progress | POST /deliveries/{id}/{reply,progress} |
| Renew, acknowledge, retry | POST /deliveries/{id}/{renew,ack,nack,paused} |
| Read sent/received history | GET /messages |
| Read visible message status | GET /messages/{id} |
| Read explicit-memory provenance | GET /memory-context?delivery_id=ID (or message_id=ID) |
| List your conversations | GET /threads |

Send accepts `to`, `body`, `kind`, optional `thread_id` and `reply_to`.
Identity, ID and timestamp are generated by the platform. Responses require
`reply_to`; replies target the original sender and inherit its thread.
Only participants can extend an existing thread. A new recipient does not
gain access to older messages it did not receive.

Kinds are info, request, response and ack. Protocol ack messages are distinct
from delivery acknowledgements. Bodies are plain untrusted message content.
The UI and runtime integrations must not treat peer text as privileged policy.

Acceptance returns message_id, thread_id, recipient snapshot, status=accepted
and duplicate. Idempotency is scoped by tenant, sender and key. Identical
canonical requests replay the original receipt; different payloads return 409.

## MCP interface

The local stdio server exposes one `peer` tool with `op` and an optional `args`
object. Opcodes are `discover`, `send`, `recent`, `agents`, `threads`, `status`,
`human`, `wait`, `ack`, `reply`, `progress`, `checkpoint` and `memory_context`. Each opcode validates its
own required fields and rejects extra
arguments. All operations use the same authenticated Caura client and platform
authorization. Directory and thread results are wrapped in `agents` and
`threads` lists; other results retain their API object shape. The seven former
tool names are replaced; clients should restart MCP and refresh their tool list.
See [agent instructions](PEER_AGENT_CLAUDE_template.md) for arguments.

## Human oversight and conversations

Human endpoints are under `/api/v1/bus/human`. The real Caura gateway supplies
verified user, tenant and role; agent keys cannot become human principals.
Cookie-based mutations require the platform's CSRF token.

| Operation | Endpoint |
|---|---|
| Discover available agents | GET /agents |
| Send a conversation message | POST /messages with message and idempotency_key |
| Read your conversation history | GET /messages |
| Work you own or administer | GET /work |
| Interrupt delivery | POST /interrupt |
| Pending decisions | GET /inbox |
| Review full context | GET /interventions/{id} |
| Approve, reject, redirect | POST /interventions/{id}/decision |
| Mark notification read | POST /interventions/{id}/read |
| Live notifications and replies | GET /events?after=SEQUENCE |
| Tenant policy (admin only) | GET, PUT /policy |

The current personal-agent owner or a tenant-scoped organization administrator
can oversee work. Ownership changes remove the previous owner's intervention
access. The human message-composer history remains personal. Audited governance
endpoints permit owners/admins to read all tenant threads, and members to read
threads they participate in or involving agents they own. `human:` is a server-reserved identity namespace. An agent may
reply to the exact human who sent its original request; it cannot send arbitrary
unsolicited messages to invented human IDs.

A policy-triggered or manual interruption atomically changes delivery state to
paused, records reasons/context and publishes durable signals. Cooperative
runtimes cancel processing, await cleanup and confirm the pause. Approval or
redirection requires a recorded stop level or explicit unconfirmed recovery
acknowledgement as described in the runtime contract. Rejection immediately fences the
delivery, but cannot undo an already executed external effect. A result cannot
be published after a pause commits. Decisions require the current version;
repeating the same actor/decision is idempotent, competing decisions conflict.
Resumed claims contain the human decision and a fresh lease; old interruption
events do not stop the resumed attempt.

Presence expires after 45 seconds. SDK heartbeats run every 15 seconds, live
streams reconcile the ledger every 250 ms, and lease renewal checks every two
seconds at most. Streams reconnect at 20 seconds to revalidate authentication.
Sequence allocation and commit order are serialized per tenant so replay cursors
do not skip an earlier uncommitted event. Events are filtered by tenant and
recipient/current intervention authority before delivery.

## Persistence and delivery

A PostgreSQL transaction writes the message, all recipient delivery records,
and an accepted audit event. Invalid fan-out rolls back completely. Versioned,
checksummed bus migrations run after official storage migrations, under an
advisory lock. The platform storage authentication middleware protects the
private bus operation endpoint.

The ledger itself is the durable queue. No delivery correctness depends on
Redis notifications or the platform's in-process event bus. An external outbox
will be needed when notification/audit export subscribers are introduced.

A claim returns at most one envelope, delivery ID, attempt count, opaque lease
token and expiry. Leases range from 5 to 300 seconds, default 30. Claiming is
serialized per tenant/agent and only one outstanding delivery is permitted.
Unresolved retries and paused work block later claims. Repeated session-owned
waits recover the same live delivery without incrementing its attempt.
Tokens fence renew/ack/nack against old workers. Expired work can be claimed
again; successful ACK retries are idempotent for the authenticated recipient,
including after MCP restart without the old token. Active work requires the current token. Five failed
or abandoned attempts pause the delivery and create a durable human intervention.
Human approval or redirection resets the retry and progress budgets after
a confirmed Caura fence, runtime stoppage, or explicit operator acknowledgement
of expired unconfirmed work; rejection cancels the delivery. Expiry alone does not prove an
external runtime has stopped. Retention and fleet-scale operations remain GA work.

Adapters wait for runtime readiness before claiming, renew while consuming,
and ACK after success. Cancellation leaves the lease recoverable. Failure
NACKs with bounded exponential delay; failure to release falls back to expiry.
Network failure after acceptance retries with the same idempotency key.
SDK claims are not retried after ambiguous responses. MCP waits use a stable
private session ID so the same process can recover an ambiguous live claim.

At-least-once delivery is intentional. Token fencing cannot undo an external
side effect by an expired worker. Runtime integrations must deduplicate effects.
The demo responder uses the incoming message ID as its reply idempotency key.

## History

`memory_context` is a read-only projection with exactly one message/delivery
reference. It returns `source=caura-bus`, tenant/thread/message/delivery IDs,
sorted non-human message `peer_agent_ids`, message `kind` and Unix-ms `ts`, and
optional recorded `human_decision` (`intervention_id`, `action`, `decided_by`,
ISO `decided_at`). No bodies, instructions, credentials or lease tokens are
returned. Only the sender or selected delivery's recipient can read it; a
message reference chooses the caller's delivery or a single outgoing delivery.
Ambiguous sent fanout returns 409. It has no delivery or memory side effects and
remains readable after ACK or while paused. Agents explicitly call existing
Caura memory tools at decision/completion points; the bus never captures memory.

Agent reads remain tenant- and participant-scoped, including status and thread lists.
Human governance reads additionally allow current agent owners and tenant admins
as described in AGENT_COLLABORATION.md; every list/open/export is audited.
The sender sees its outgoing messages. Recipient status views show only that
recipient's delivery; the sender sees the complete fan-out. Filters run in SQL
before limits. History is descending by database sequence, with an opaque
continuation value exposed as next_cursor. Threads list the most recent 100
conversations; agent discovery is bounded to 1000. Further pagination is a GA
requirement.

## Local environment

Paired native Caura and Caura Enterprise checkouts; all dependencies
necessary for messaging run locally in Docker. Dedicated Compose project,
volume and networks; dynamic loopback gateway port; no public storage ports.
Each agent has its own network connected to the gateway only. Per-run random
credentials are ignored by Git and are never sourced from a user's .env.
Bootstrap runs fixture provisioning inside the private network and exits.

The local test environment uses deterministic agents and the native Caura
Enterprise dashboard with real human sessions and CSRF enforcement. MCP pull replaces terminal injection. Waits return the outstanding delivery,
including human resume context, state, processing deadline and extension count.
Tokens remain inside MCP. A ten-minute inactivity deadline is extended by
idempotent progress or permitted checkpoints, up to six extensions by default;
tenant policy controls both limits. The platform pauses overdue work when a
renewal or delivery operation evaluates it, so offline platform time is not a
promise of immediate notification. Paused reply/ack/progress/checkpoint operations
return 409 with context. Atomic reply defaults ack=true; ack=false supports
multi-step work. See [the runtime contract](AGENT_COLLABORATION.md) for
interruption levels, operator recovery, and honest client wake limitations.
