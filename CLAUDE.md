# CLAUDE.md — caura-memclaw operating manual

MemClaw: fleet memory for AI agents. Python 3.12 monorepo (FastAPI + MCP + Postgres/pgvector)
with a TypeScript OpenClaw plugin. This file is the project operating manual — read it before
your first edit. Global rules (`~/.claude/rules/*`) still apply; this file adds the
repo-specific layer and wins on repo-specific conflicts.

## 1. Map

| Directory | What it is | The one rule |
|---|---|---|
| `core-api/` | FastAPI app + FastMCP server (`mcp_server.py`), business logic (`services/`), recall pipeline (`pipeline/`), tool registry (`tools/`) | **Never writes SQL.** All storage access goes through `core-api/src/core_api/clients/storage_client.py` (HTTP → core-storage-api). |
| `core-storage-api/` | Owns Postgres + pgvector. The only service with SQL. | New query = new storage endpoint here + a `storage_client` method, not inline SQL elsewhere. |
| `core-worker/` | Background enrichment (deferred deployment mode). | Tests default to `DEPLOYMENT_MODE=inline`; deferred-path tests override explicitly. |
| `core-operations/` | Ops/observability glue. | |
| `common/` | Shared SQLAlchemy models (`common.models.*`). Alembic config at repo root. | Model change ⇒ migration in the same PR (see §4.10). |
| `plugin/` | TypeScript OpenClaw plugin. `plugin/tools.json` is **generated** from the registry. | Never hand-edit `tools.json`; run `scripts/export_tool_specs.py`. |
| `tests/` | Root-level suite spanning all services (~3800 tests). | See `/run-tests` skill before invoking anything. |
| `sprints/` | Sprint plans (`capability_tasks.json`) + signoffs. | Source of truth for in-flight work; resume from disk, never from conversation memory. |
| `docs/` | `api-surfaces.md` (surface ownership charter), `MEMCLAW_CLIENT_GUIDE.md` (agent-facing tool manual + session-close protocol), `performance.md`, `local-embedder.md`. | |
| `scripts/` | Smoke tests, wet tests, repro scripts, `export_tool_specs.py`. | New MCP tool needs a wet test against the local docker stack. |

**Three callable surfaces** — REST, MCP, OpenClaw plugin — are intentionally **asymmetric**.
`docs/api-surfaces.md` is the charter for which surface owns what. Never mirror an operation
across surfaces "for symmetry."

## 2. How work happens here (conventions)

### Existing conventions — follow exactly

1. **Sprint protocol.** Multi-step work is planned with `/sprint-plan` into
   `sprints/sprint-<slug>/capability_tasks.json` (WorkItems: `id`, `objective`,
   `acceptanceCriteria`, `state`, `dependencies`), committed to a `sprint/<slug>-plan` branch
   **before** execution, executed with `/sprint-run`, and closed by a
   `SPRINT-<SLUG>_SIGNOFF.md` written as the final WorkItem (`*-Z01`). Acceptance criteria cite
   `file:line` and name the exact reuse targets.
2. **Conventional Commits with scope**, e.g. `feat(RL-03): wire reasoning_mode ...`,
   `sprint(recall-reasoning-loop): RL-Z01 — sprint signoff`. Sign off every commit (DCO):
   `git commit -s`. One WorkItem ⇒ at least one commit naming its ID.
3. **Commit gate.** A PreToolUse hook (`.claude/hooks/pre-commit-check.sh`) blocks `git commit`
   unless per-service `ruff check`, `ruff format --check`, and `mypy` pass for `core-api` and
   `core-storage-api`. Run them the same way the hook does:
   `uv run --project core-api ruff check core-api/` etc. Never bypass the hook; fix the code.
4. **Additive-only hot paths.** New behavior on the recall/write path ships as an **opt-in
   parameter** whose default leaves the existing call sequence byte-identical, plus a
   ratio-based latency guard test (pattern: `tests/pipeline/test_pipeline_latency.py` — assert
   a percentage ceiling against a same-run baseline, never absolute milliseconds).
5. **Never-raises loops.** Orchestration/loop code (e.g. `graph_reasoning_loop.py`)
   catches-and-degrades at both the per-dispatch and outer-loop level; a failed step returns an
   empty/neutral result, it does not propagate. Tests then assert exact degraded shapes.
6. **Grounded reuse.** Prefer wrapping an already-tested primitive (and citing it by
   `file:line` in the plan) over writing new storage/service code.
7. **Memory protocol.** MemClaw session loop (keystones → recall → work → write/evolve) per
   `~/.claude/rules/brain.md`; session-close sequence in `docs/MEMCLAW_CLIENT_GUIDE.md` §4d.
   Two live gotchas: `fleet_id` is **not** guaranteed to be the repo slug (a FORBIDDEN error
   names the correct fleet — retry with that, don't debug), and MemPalace falls back to a
   default wing silently.
8. **RTK.** A hook rewrites common commands through `rtk` for token savings — transparent;
   don't fight it.

### Added conventions — adopt these

9. **Regenerate, don't reconcile.** Anything generated (`plugin/tools.json`, the three
   `tests/fixtures/*_baseline_v1.json` files) is regenerated by script after a change, never
   patched by hand to make a diff pass.
10. **Counts are computed, never copied.** Before writing any number into docs or a signoff
    (tool counts, test counts, token ceilings, latencies), produce it with a command in the same
    session (`grep -c`, `pytest -q` tail, `python -c "...len(REGISTRY)"`). Both the tool catalog
    (15→20) and the token ceiling (fixtures README said 5000; the test enforces 7500) have
    drifted this way before.
11. **Pre-existing failures get their own commit.** If the suite is red before your change,
    prove it (`git stash && pytest <failing> && git stash pop`), then either report it or fix it
    in a separate commit labeled as a pre-existing repair — never bundled into your feature
    commit.
12. **Verify the wiring, not the diagram.** Before citing or modifying a call chain, grep the
    actual **call site** of the entry point and trace downward. Function definitions prove
    existence, not participation.

## 3. Commands that actually work

```bash
# Environment — system Python lacks pgvector; ALWAYS activate first
source .venv/bin/activate

# Full test suite (test-db port may be remapped — check `docker ps` first; see /run-tests)
TEST_DATABASE_URL="postgresql+asyncpg://memclaw:changeme@127.0.0.1:5433/memclaw" \
  python -m pytest tests/ -q

# Lint/type gates, exactly as the commit hook and CI run them (per service, via uv)
uv run --project core-api ruff check core-api/
uv run --project core-api ruff format --check core-api/
uv run --project core-api mypy --config-file core-api/pyproject.toml core-api/src/
uv run --project core-storage-api ruff check core-storage-api/
uv run --project core-storage-api ruff format --check core-storage-api/
uv run --project core-storage-api mypy --config-file core-storage-api/pyproject.toml core-storage-api/src/

# Regenerate the plugin tool manifest after any registry/description change
PYTHONPATH=core-api/src:core-storage-api/src:. python scripts/export_tool_specs.py

# Local dev stack (Postgres+pgvector, Redis, hot-reload API)
docker compose -f docker-compose.dev.yml up -d

# Migrations (CI runs this before tests)
alembic upgrade head
```

## 4. Named failure modes — and the rule that prevents each

These are mistakes actually made (or narrowly avoided) in this repo. Each has a name so it can
be cited in reviews and signoffs.

1. **The Phantom Layer.** Wiring a feature through a function that exists but is not on the
   real call path (RL-03: a dead `recall_service.recall()` hop, found only at verification).
   *Rule:* before wiring, grep the entry point's call site and trace one real request downward;
   cite the call site's `file:line`, not the definition's.
2. **The System-Python Trap.** Running `pytest` outside `.venv` — imports fail on `pgvector`
   with misleading errors. *Rule:* `source .venv/bin/activate` is line one of every test recipe.
3. **The 5432 Guess.** `tests/conftest.py` defaults `TEST_DATABASE_URL` to port 5432, but the
   dedicated test container has been mapped to 5433. *Rule:* `docker ps` first; pass
   `TEST_DATABASE_URL` explicitly; never "fix" conftest's default.
4. **The "It's Marked Unit" Illusion.** Session-scoped `autouse` fixtures in
   `tests/conftest.py` force real-Postgres setup for essentially the whole suite, `unit` marker
   or not. *Rule:* a running test DB is a precondition for any pytest invocation; a connection
   error means environment, not code — do not start mocking the DB to make it pass.
5. **Baseline Blindness.** Any edit to a tool description, parameter, or docstring — even
   punctuation or a ruff reformat (see commit `a21ae87`: en-dash→hyphen drifted two baselines) —
   breaks `test_tool_descriptions_regression.py`, `test_mcp_token_budget.py`, and
   `test_tools_export_in_sync.py`. *Rule:* touching `core_api/tools/` or `mcp_server.py` ⇒ run
   the `/tool-surface` skill checklist before committing.
6. **Stale-Count Documentation.** Hardcoded counts in prose drift (tool catalog said 15 when
   there were 20; fixtures README still says a 5000-token ceiling vs the enforced 7500).
   *Rule:* convention 10 — compute every number at write time; update the count **and** its
   guard constant (`EXPECTED_TOOL_COUNT`) in the same commit.
7. **The Symmetry Reflex.** Adding an MCP tool because REST has it (or vice versa).
   *Rule:* justify against `docs/api-surfaces.md` — read-only aggregations are free; everything
   else needs a today-blocked agent workflow, and should extend an existing tool's `op=` before
   adding a top-level tool.
8. **Raw-String Errors.** Returning `"Error (422): ..."` strings from MCP tools — a dedicated
   CI grep gate blocks this. *Rule:* use the structured error shape used by existing tools in
   `core_api/tools/`; copy a neighbor, don't invent.
9. **SQL Where It Doesn't Belong.** Writing SQL or a new SQLAlchemy query inside core-api.
   *Rule:* the query lives in core-storage-api behind an endpoint; core-api gets a
   `storage_client` method. If you're importing `sqlalchemy` in `core-api/src`, stop.
10. **ORM/Migration Drift.** Changing `common/models/*` without an Alembic migration (or vice
    versa) — this has required dedicated repair commits (`b501faa`, `b0df5e9`). *Rule:* model
    change and migration in the same commit; verify with `alembic upgrade head` against a fresh
    test DB before claiming done.
11. **Moving the Goalposts.** Loosening a latency ceiling, raising `CEILING_TOKENS`, or
    regenerating a baseline just to turn CI green. *Rule:* guards exist to fail. Regenerating a
    baseline is correct only when the surface change itself was intended and reviewed; changing
    a threshold requires explicit user sign-off, stated in the commit body.
12. **Root-Level Ruff.** Running plain `ruff`/`mypy` from the repo root with the wrong config
    scope, then "fixing" style that CI never checks (CI scopes to each service's `src/`).
    *Rule:* run the gates exactly as §3 shows — per service, via `uv run --project`.
13. **The Fleet-Slug Assumption.** Passing `fleet_id="caura-memclaw"` to MemClaw writes because
    that's the repo name. *Rule:* on a fleet-policy FORBIDDEN, the error message names the
    writable fleet — use it and move on.
14. **Trusting a Cached Schema After Deploy.** After redeploying core-api, this session's own
    MCP client still holds the old tool schema — new params "don't exist." *Rule:* verify a
    fresh deploy via raw `curl` to `/mcp` (JSON-RPC `tools/call`), never via the session's
    cached MCP tools. See the `/deploy-53` skill.
15. **Fixing the Test Instead of the Code.** Editing an assertion so it matches observed
    behavior without establishing which side is wrong. *Rule:* a failing test earns a diagnosis
    line first ("test wrong because X" / "code wrong because Y") — in the commit body if you
    change the test.

## 5. Quality bar per deliverable — checkable, not adjectives

A deliverable is done when every box checks. "Compiles" and "looks right" are never checks.

**Feature / fix (code):**
- [ ] Acceptance criteria written before code (in the sprint plan or stated in-conversation).
- [ ] New feature ⇒ behavior tests through the public surface; bug fix ⇒ a regression test that
      fails on the pre-fix code (actually run it against the pre-fix code once).
- [ ] Full suite green locally with the §3 invocation; count reported from pytest output.
- [ ] All six §3 lint/type gates pass.
- [ ] Hot-path change ⇒ opt-in param + ratio-based latency guard (convention 4).
- [ ] Every changed line traces to the task; no drive-by refactors (simplicity/surgical rules).

**Test file:**
- [ ] Asserts behavior via public API (HTTP route, MCP tool, service function) — not private
      helpers or DB rows reached around the interface.
- [ ] Passes standalone (`pytest tests/test_x.py -q`) *and* inside the full suite.
- [ ] Unique data per run via `tests/conftest.py`'s `uid()` — no fixed strings that 409 on rerun.
- [ ] Timing assertions are ratios against a same-run baseline; zero `sleep`-based waits.
- [ ] Marked `unit` / `integration` / `benchmark` per `pytest.ini`.

**Migration:**
- [ ] Paired with its model change in one commit.
- [ ] `alembic upgrade head` passes on a fresh DB; full suite passes after it.
- [ ] No edits to already-shipped migration files.

**MCP tool-surface change:** the `/tool-surface` skill checklist, in full. Summary:
registry + wet test + regenerated `plugin/tools.json` + regenerated baselines +
`EXPECTED_TOOL_COUNT` + client-guide catalog + token budget green + charter justification.

**Docs:**
- [ ] Every count/number produced by a command this session (convention 10).
- [ ] Every command block actually executed once, copy-paste-clean, from the stated cwd.
- [ ] Relative links resolve (`ls` the target).

**Sprint plan (`capability_tasks.json`):**
- [ ] Valid against the existing schema (copy a previous sprint's shape; IDs from backlog, never
      invented).
- [ ] Every WorkItem has acceptance criteria that are runnable checks (test name, command,
      observable output).
- [ ] Every `file:line` citation re-verified against current code, call-site traced (§4.1).
- [ ] Last WorkItem is the signoff doc. Plan committed before execution begins.

**Sprint signoff:**
- [ ] Metrics table cross-checked against `git log` (commit hashes real, counts computed).
- [ ] Each acceptance criterion listed with the observed evidence (test output, ratio numbers).
- [ ] "What to improve" items are actions, not observations.

**Commit / PR:**
- [ ] Conventional type(scope) subject; `-s` DCO sign-off; one logical change.
- [ ] Hook gates passed (never `--no-verify`).
- [ ] Body states any threshold/baseline change and why (§4.11).

## 6. When uncertain — exact escalation rules

**Proceed silently** (no question, no assumption note): reversible, in-scope, and covered by a
convention above — e.g. which test file a regression test goes in, variable naming, standard
fixture use.

**Proceed, but state the assumption in one line** when there are multiple reasonable readings
and they converge on similar code — pick the likeliest, flag it: *"Assuming X; say the word and
I'll flip it."* Batch such assumptions; never interrupt mid-task for them.

**Stop and ask one focused question** — before writing code — when any of these hold:
1. The answer exists only in Leon's head or infra: hostnames, credentials, which fleet/tenant,
   business rules, whether a live consumer depends on a shape you want to change.
2. Two readings lead to **meaningfully different code** (different surface, different schema,
   different public behavior).
3. The task as stated violates a charter or invariant here (asks to mirror a surface, put SQL in
   core-api, make a hot-path change non-optional). Name the conflict, propose the compliant
   version, ask which he wants.

**Always stop and confirm, even mid-task, even if previously "approved" in another context:**
- Anything destructive or hard to reverse: dropping/resetting a DB, force-push, deleting
  uncommitted work, bulk-delete ops against a live MemClaw store.
- Deploying to any live host (utility-53 / 192.168.1.53 included).
- Raising `CEILING_TOKENS`, loosening a latency ceiling, or any baseline regeneration whose
  cause you cannot name as an intended surface change.
- Adding a new **top-level** MCP tool (vs an `op=` extension), changing trust-level gates, or
  any breaking change to the Public API (`feat!` / `BREAKING CHANGE`).
- Editing already-shipped Alembic migrations.

**When blocked mid-sprint:** do not repair the plan in flight. Mark the WorkItem failed with the
reason, continue WorkItems that don't depend on it, and record the failure + proposed plan fix
in the signoff. If the plan itself is invalid, fail fast back to `/sprint-plan`.

**When a check fails and you don't know why:** stop cascading. Reproduce it in isolation, write
the one-line diagnosis (§4.15), and only then continue. Two consecutive undiagnosed failures ⇒
report state honestly and ask.
